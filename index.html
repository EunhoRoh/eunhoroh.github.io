Decision 01 · 레거시에 부수지 않고 얹기

Decision 02 · 프라이버시를 서버 계약으로

부모가 볼 수 있는 것은 자녀가 정한다 — 회귀 테스트로 고정

상황 — 부모가 자녀의 일기를 보는 구조는 그대로 만들면 감시가 됩니다. 결정 — 공개범위 3단계(전문/요약/비밀)를 직렬화 단계에서 강제. 비밀 글은 응답에 아예 없고(감정 점수 같은 파생 데이터까지), 요약은 serializer 마스킹, 남의 것은 404. 부모가 자녀의 공개범위를 대신 바꿀 수 없다는 규칙은 회귀 테스트로 고정. 저장이 비동기 파이프라인이라 저장 응답에 id가 없는 문제는, id가 처음 생기는 폴링 시점에 보호적 기본값으로 수렴하는 fire-and-forget 훅으로. 같은 백엔드라도 토큰 수명은 데이터 민감도에 맞춰 단기 액세스 + 리프레시 회전으로 재평가.

→ 신뢰 규칙이 UI 문구가 아니라 데이터가 나가는 마지막 관문에서 지켜짐. family 백엔드 테스트 111건.

Decision 03 · 내가 만든 것을 버리는 결정

상황 — 부모앱(Flutter)은 작성 앱보다 어른용 조회 대시보드(교사웹, React)에 가까웠고, 제가 만든 가족톡방은 기존 공유이야기와 겹쳤습니다. 결정 — 8월 18일, 부모앱을 React 18 + TypeScript로 재구현(백엔드 무변경, Flutter 원본은 스펙·롤백 경로로 보존)하고 톡방은 폐지. Flutter 62파일 14,475줄을 전수 인벤토리해 포팅 대상 58파일을 정하고, 디자인 토큰을 CSS 변수로, API 경로를 상수로, 401이면 refresh 한 번 재시도하는 클라이언트를 만든 뒤 홈 8섹션·일기 상세·감정 달력·리포트·알림함·마이페이지·가족 피드를 이식.

→ 이틀 만에 전 화면 이식, tsc·oxlint 0, 테스트 서버에 올림. 프로토타입의 가치는 코드가 아니라 "이 설계가 동작한다"는 증거였습니다.

Decision 04 · 프롬프트를 실측으로 고치기

AI '오늘의 질문' — 안전 판정을 먼저, 모델은 나중에

상황 — 자녀의 최근 일기로 부모용 대화 스타터를 만드는 기능(gpt-4o-mini). 첫 버전은 요약공개로 가린 일기의 내용을 질문이 되풀이해 마스킹을 우회했고, 영어 일기에 한국어로 답했습니다. 결정 — 11사례×2회 실측으로 세 번 고쳤습니다. 한 줄 지시 → 안전 판정을 먼저 하는 2단계 JSON → 언어 규칙 분기, 고위험 표현은 모델을 부르기 전에 규칙으로 SKIP, 일기의 구체어를 되풀이하면 1회 재생성 후 SKIP. 24시간 만료, 질문이 없으면 카드를 숨김.

→ 위험 유형 5종 전부 SKIP, 영어·스페인어 정상. 남은 약점(설렘 일기 과잉 SKIP)은 안전 쪽 실패라 수용. 테스트 12종 추가.

Decision 08 · AI 서비스 통합

위험을 놓치지 않는 통합 — 게이트, fail-safe, 공인시험

설계 — 모든 일기를 SLM에 보내는 대신 GPT 감정점수 9점 이상만 통과시키는 1차 게이트로 호출량을 제어하고, 위험군만 SLM 서버에 HTTP로 위기단계 분류 요청(timeout 10초). 호출 실패 시에는 응급으로 간주하는 fail-safe — "놓치는 것보다 과잉 대응이 낫다"를 코드로 구현. 응급 판정 시 학생에게 13개 언어별 핫라인을 동기 노출, 교사에게 암호화 알림은 비동기. 백엔드에 ML 의존성 없음(HTTP로 라벨만) — 모델이 교체돼도 서비스는 무변경.

Decision 09 · 비대칭 타임아웃 설계

→ 피크시간 실제 응답시간을 정량 측정하면서 알림 폭주 0건. 모니터링 주기와 측정 심도를 맞바꾸지 않는 구조.

Decision 10 · 사고 재발 방지

소셜 로그인 장애, "사용자 문의"에서 "30분 내 자동 탐지"로

상황 — 과거 운영 .env의 GOOGLE_CLIENT_ID 누락으로 구글 로그인이 전면 실패했는데, 사용자 문의로만 인지한 사고가 있었음. 결정 — refresh_token 기반으로 Google SSO를 두 GCP 프로젝트에서 30분마다 자동 검증하는 Bot B를 신설. refresh_token은 백엔드가 쓰는 client_id로 발급해야 aud 검증을 통과한다는 점, OAuth consent가 Testing이면 7일 만료된다는 점 등 함정을 사전에 해결. Provider 추상화로 Apple 등 확장 구조 확보.

→ 동일 유형 장애의 탐지 시간 상한이 30분으로 고정. 계정은 YAML 데이터화, 비밀은 env 분리로 유지보수 비용 최소화.

Decision 11 · 근본 원인 추적

로그 한 줄 없이 죽는 배치, OOM에서 N+1까지

상황 — 뱃지 승급 배치가 38,230명 처리 중 절반쯤에서 에러 로그 없이 중단. 추적 — "Start만 찍히고 에러가 없다" → 프로세스 강제 종료 → OOM 가설 → 코드 리뷰로 유저마다 행성 데이터 전체를 재쿼리해 리스트에 적재하는 N+1 + 메모리 누적 패턴 발견(ForkPoolWorker OOM). 설계 — ① 행성별 1회 쿼리 + 경험치순 정렬 ② status_map 사전 판정 ③ iterator(chunk_size=500) + 사전 로드의 3단계로 재설계.

→ 쿼리 38,230회 → 행성 수(5~6회)로 재설계, 최적화 버전 운영 배포(2026.07). (같은 패턴 재현 데모: django-n-plus-one-lab — 5,000명 더미 실측: 쿼리 5,998→11회, 379초→0.24초. 데모 재현치이며 운영 측정치는 아닙니다)

Decision 12 · 구조로 예방

회사에서 사후에 찾은 N+1을, 여기선 처음부터 생기지 않게

상황 — 회사에서 38,230명 배치가 N+1로 메모리가 터지는 걸 사후에 추적해야 했습니다. 개인 프로젝트에선 같은 일을 리뷰가 아니라 구조로 막고 싶었습니다. 결정 — 전 관계 LAZY + 전역 batch fetch, 조회 화면은 DTO/id 프로젝션으로 "오늘의 루틴 + 완료 여부"는 쿼리 2번(루틴 목록 + 오늘 도장 id 집합), 캘린더는 group by 1번. 소유권 검증은 findByIdAndMemberId 조건으로 프록시를 건드리지 않고, OSIV는 끔. 하루 한 번 도장은 unique(routine_id, stamp_date)로 DB가 막습니다. 착용 아이템 전환은 JPQL 벌크 UPDATE 1회 — clearAutomatically가 앞서 조회한 엔티티를 떼어 내는 함정은 리뷰에서 잡았습니다.

→ 핵심 화면 쿼리 수가 데이터 양과 무관하게 고정. 경험이 설계 원칙(docs/07 개발원칙)으로 이어진 사례.

Decision 13 · 요구를 먼저, 수단은 나중에

주식 앱을 접고, FCM을 빼고, LLM은 인터페이스 뒤로

아이디어 — 첫 후보는 "1,000원에 AI 추천 종목 3개" 앱이었는데, 대가를 받는 종목 추천은 유사투자자문업 신고 대상이라 접었습니다. 알림 — FCM 대신 기기 로컬 알림. 루틴 시간은 기기가 이미 아는 정보라 서버가 보낼 이유가 없었고, Firebase 프로젝트·토큰 관리·서버 스케줄러가 빠졌습니다. 동기화는 전부 취소 후 재등록으로 멱등하게. AI 플랜 — 생성기 인터페이스를 먼저 두고 룰 엔진으로 6개 테마를 내보냈습니다. LLM은 구현체만 바꾸면 붙습니다(아직 연결 안 함).

→ 서버 인프라 세 가지 없이 알림 완성, AI 기능은 원가 0으로 먼저 검증. "만들 수 있는가"보다 "출시할 수 있는가"를 먼저 물었습니다.

정직하게: 3주 동안 AI 플랜 단계까지 만들었고 스토어 배포는 하지 않았습니다(Expo로 실행). Spring Boot 4로 올라가며 겪은 MockMvc 모듈 분리·Jackson 3 전환은 Gradle 캐시의 jar를 열어 확인했습니다.
